# Run a Scheduler

PayStreamer is built on a decentralized execution model. Smart contracts cannot execute themselves at a specific time; they require an external crank. 

Instead of relying on a centralized, trusted backend to process subscription payments when they are due, PayStreamer incentivizes an open network of **Schedulers** to process payments on behalf of users.

## The 1% Incentive

Whenever a payment is successfully processed, the protocol collects a **3% flat transaction fee**. 

- **2%** goes to the Protocol Treasury (funding long-term development).
- **1%** goes directly to the **Scheduler** who executed the transaction!

This means anyone can run a scheduler and earn passive income in `PUSD` simply by keeping the protocol's payments flowing on time.

## How Schedulers Work

A scheduler is fundamentally an off-chain worker. It can be built using any technology—a robust Node.js + BullMQ server, a lightweight edge function, or even a browser extension!

The core loop of a scheduler is simple:

### 1. Discover Due Subscriptions

There is **no due-payment event to subscribe to** — payment schedules live in
account state, not in an event stream. A scheduler polls:

1. Query `PlatformRegistered` events to find platforms.
2. Query `SubscriptionCreated` events to find the `SubscriptionAccount` objects
   subscribed to each one.
3. Read those account objects and compare each subscription's
   `next_billing_time` against the on-chain `Clock` (`0x6`).

Anything whose `next_billing_time` has passed is due now. This is exactly what
`packages/scheduler-core`'s `discovery.ts` does, and it is worth reading before
writing your own.

<Callout type="warning">
  **Check the coin type carefully.** A subscription's account holds
  `Coin<T>`, while the platform tier declares the currency it settles in.
  `process_due_payment` does **not** check those against each other on-chain,
  so a mismatched account can be billed in the wrong coin. Compare them
  *canonically*: an account's type comes from its object type string and
  carries the `0x` prefix, while a tier's `denomination` is a Move `TypeName`
  that gRPC encodes **without** one. A naive string comparison reports a
  mismatch between a coin and itself.
</Callout>

### 2. Execute the PTB

Once a payment is due, the scheduler builds and signs a Programmable
Transaction Block calling `process_due_payment`.

Using the PayStreamer SDK, this looks like:

```typescript
import { buildProcessPaymentTx } from "@paystreamer/sdk/core";
import { Transaction } from "@mysten/sui/transactions";

const tx = new Transaction();

buildProcessPaymentTx({
  tx,
  packageId: "0xPAYSTREAMER",
  registryId: "0xREGISTRY",
  clockId: "0x6",
  denomination: "0x...::pusd::PUSD",
  accountId: "0xUSER_ACCOUNT",
  platformId: "0xPLATFORM",
  platformInitVersion: 1, // obtained from RPC
  // The protocol's single shared PaymentScheduler object — the same id for
  // everyone on a given network, not something you own or register.
  schedulerId: "0xPAYMENT_SCHEDULER",
  schedulerInitVersion: 1,
});

// Sign and execute with your scheduler's private key
const result = await client.signAndExecuteTransaction({
  transaction: tx,
  signer: yourKeypair,
});
```

### 3. Earn

When the transaction succeeds, `process_due_payment` deducts the subscription
amount from the subscriber, routes the platform's cut, and transfers your 1%
fee as a fresh `Coin<T>` to **whichever address sent the transaction**
(`ctx.sender()`).

That has one consequence worth knowing: since the fee recipient is the sender,
`PaymentProcessed` carries a `scheduler_fee` amount but **not** the address it
was paid to. To total your earnings, query `PaymentProcessed` events filtered
by `sender` and sum `scheduler_fee`:

```graphql
query schedulerFees($type: String!, $sender: SuiAddress!) {
  events(filter: { type: $type, sender: $sender }, first: 50) {
    pageInfo { hasNextPage endCursor }
    nodes {
      timestamp
      transaction { digest }
      contents { json }
    }
  }
}
```

<Callout type="warning">
  **Don't compute earnings from your coin balance.** The fee lands as a real
  `Coin<T>`, so watching your balance looks tempting — but if you also operate
  the platform or the protocol treasury (as on the demo deployment, where all
  three are the same address), your balance moves by the *full billed amount*
  rather than your 1% cut. `scheduler_fee` is the only correct source.
</Callout>

## Getting Started

**No registration is required.** Running a scheduler is permissionless: there
is no `Scheduler` object to create and no allowlist to join. `PaymentScheduler`
is a single shared object owned by the protocol, identical for every scheduler
on a network. All you need is:

- a funded Sui address to pay gas, and
- a process that polls for due payments and submits the PTB above.

The first scheduler to land a transaction for a given due payment collects the
fee, so in practice schedulers compete on latency and reliability.

## Run the browser extension

`apps/extension` packages the scheduler as a Chrome MV3 extension: install it,
leave your browser open, and it bills due payments in the background.

```sh
pnpm --filter @paystreamer/extension build
```

Then in Chrome: open `chrome://extensions`, enable **Developer mode**, choose
**Load unpacked**, and select `apps/extension/dist`. The extension generates a
signing key on first run and shows its address — fund that address with a small
amount of SUI for gas (the popup has a testnet faucet button), and it starts
earning on the next cycle.

<Callout type="warning">
  **Its signing key is stored unencrypted** in `chrome.storage.local`. A
  scheduler signs every cycle unattended, so it cannot prompt a wallet or hold
  a passphrase a suspended service worker would forget. Treat it as a
  low-value key holding only gas and accrued fees — never import an address
  you keep other funds on.
</Callout>

Two limits worth knowing before you install it:

- **Cycles run at most once per minute.** `chrome.alarms` cannot go faster, and
  a suspended MV3 service worker loses `setInterval` timers entirely. The
  standalone service polls every 10 seconds, so it will usually win a contested
  payment.
- **Your browser must be running** for cycles to fire.

The extension is distributed unpacked rather than through the Chrome Web Store.
